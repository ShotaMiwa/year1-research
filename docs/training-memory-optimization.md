# 学習時のメモリ・計算の工夫（説明用）

トピック損失の計算で、発話をエンコードする際にメモリを抑えるために行っている工夫をまとめます。

---

## 1. 何を問題にしているか

- トピック損失では、**対話の全発話**（`topic_train`）に対する埋め込みが必要になる。
- 対話が長いと発話数が多く、**全発話を一度に BERT などでエンコードすると GPU メモリが足りなくなる**可能性がある。
- そこで「全発話を一括エンコードしない」「使った中間テンソルはすぐ捨てる」という方針で工夫している。

---

## 2. 工夫①：ローカルウィンドウだけをエンコードする

**やっていること**

- 対話全体ではなく、**「現在注目している発話」の前後だけ（ローカルウィンドウ）** を切り出して、その範囲の発話だけをエンコードする。
- バッチ内の**サンプルごと**にループし、各サンプルでは「そのサンプルの現在発話 ± `window_size` 発話」だけを `encode_topic` に渡す。

**コード上のイメージ**

- `topic_train` は「バッチ内の全サンプルの全発話が連結された長いテンソル」。
- 各サンプルについて:
  - `current_utt`（現在発話のインデックス）の前後 `window_size` で `start_idx`, `end_idx` を決める。
  - `local_topic_train = topic_train[offset + start_idx : offset + end_idx]` で**ウィンドウ内の発話だけ**を取り出す。
  - `encode_topic(local_topic_train, ...)` で**そのウィンドウだけ**をエンコードする。

**効果**

- 一度にエンコードする発話数が「対話全体」ではなく「ウィンドウ長（だいたい 2×window_size+1 程度）」に抑えられる。
- 長い対話でも、ウィンドウ長が固定なので **メモリ使用量が対話長に比例して増えにくい**。

**該当コード**（`src/models/training.py` の `_compute_topic_loss` 内）

- ウィンドウ範囲の計算: 209–213 行目付近  
- ウィンドウのスライスとエンコード: 215–221 行目付近  

---

## 3. 工夫②：使った埋め込みをその都度解放する

**やっていること**

- 各サンプルで、ローカルウィンドウをエンコードした結果（`local_fused`）を使って疑似セグメンテーションと損失計算を行う。
- そのサンプルの処理が終わったら、**次のサンプルに進む前に `del local_fused` で参照を捨てる**。

**効果**

- 同じバッチ内で「前のサンプルの埋め込み」を保持し続けないので、**ピーク時の GPU メモリが増えにくい**。
- ループでたくさんサンプルを処理しても、常に「いまのサンプル用の埋め込み 1 つ分」程度の追加メモリで済む。

**該当コード**（`src/models/training.py`）

- 240–242 行目付近: コメント「メモリ解放」と `del local_fused`。

---

## 4. まとめ（他人に説明するときの一文）

- **「トピック損失では、全発話を一括でエンコードせず、サンプルごと・現在発話の前後のウィンドウだけをエンコードし、使った埋め込みはそのサンプルが終わるたびに `del` で解放している。そのことで長い対話でもメモリを抑えている。」**

---

## 5. 補足：マージン損失まわりは一括エンコード

- マージン損失（グローバルな pos/neg スコア）用の topic ベクトル（`topic_context`, `topic_pos`, `topic_neg`）は、**バッチ単位で一括エンコード**している（`forward` 内 82–95 行目付近）。
- こちらは「対話の全発話」ではなく、データ側で用意した context/pos/neg のまとまりだけなので、上記のウィンドウ＋ループ＋`del` の工夫はトピック損失の経路にのみ入れている、という整理になる。
